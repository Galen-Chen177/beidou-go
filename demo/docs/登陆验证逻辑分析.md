## 完整数据流（从 TCP 到 Handler）

`LoginPasswordHandler` 拿到的 `InPacket` 并非原始 TCP 数据，而是经过多层解码后的**明文**。完整链路如下：

```
TCP 原始字节
  │
  ├─[GMSV83PacketProtocol.decode()]
  │   ├── 1. 读 4 字节包头（header）
  │   ├── 2. 校验包头合法性（IsValidHeader）
  │   ├── 3. 解码包体长度（decodePacketLength）
  │   ├── 4. 读 N 字节包体
  │   ├── 5. AES-OFB 解密（crypt，XOR 流密码）
  │   └── 6. 自定义反混淆（decryptData，6 轮 shuffle）
  │
  ├─ 解密后的明文 → 包装为 ByteBufInPacket
  │
  ├─[PacketProcessor]
  │   └── 读 2 字节 opcode → 路由到对应 Handler
  │
  └─[LoginPasswordHandler.handlePacket()]
      ├── readString() → login
      ├── readString() → pwd
      ├── skip(6)      → 填充
      └── readBytes(4) → hwid
```

## 1. 加密握手：Hello 包与 IV 交换

### 为什么需要加密

客户端与服务器之间走 TCP 长连接。如果明文传输，账号密码可直接被抓包工具读取。因此所有游戏数据包都需要加密。

### 加密算法概述

- **AES**：最常用的对称加密算法（加密和解密用同一个 key）。本项目使用 **AES-256**（32 字节密钥），key 硬编码在 [MapleAESOFB.java:38-47](../gms-server/src/main/java/org/gms/net/encryption/MapleAESOFB.java#L38-L47)
- **OFB 模式**：AES 本身只能加密固定 16 字节的块，OFB 是一种"模式"，让它能处理任意长度的数据。核心思路：**用 AES 不断生成"密钥流"，把密钥流跟数据 XOR**
- **XOR 对称性**：`A XOR B = C`，`C XOR B = A`（XOR 两次同一个值就还原），所以加密和解密是**完全相同的操作**

### IV（Initialization Vector，初始向量）

IV 是 OFB 模式的"种子"。**同一个 key + 同一个 IV 产生完全相同的密钥流**。每次连接用不同的 IV（随机数），保证每次的密文不同。

IV 结构（[InitializationVector.java:14-22](../gms-server/src/main/java/org/gms/net/encryption/InitializationVector.java#L14-L22)）：

```java
// 服务端"发送方向"的 IV（服务端加密 → 客户端解密）
generateSend()    → {82, 48, 120, randomByte}   // ASCII: "R0x" + 随机

// 服务端"接收方向"的 IV（客户端加密 → 服务端解密）
generateReceive() → {70, 114, 122, randomByte}  // ASCII: "Frz" + 随机
```

- `"Frz"` 和 `"R0x"` 是开发者的个人标记（名字缩写），技术上不重要
- 第 4 字节是随机数，保证每次连接密钥流不同
- `generateReceive()` 的返回值就是服务端用来**解密客户端数据**的 IV（`recvIv`）

### Hello 包格式

Hello 包是**唯一明文发送**的包，在 TCP 连接建立后立即发送，用于交换 IV。格式（[PacketCreator.java:589-598](../gms-server/src/main/java/org/gms/util/PacketCreator.java#L589-L598)）：

```
偏移  字节           含义
───────────────────────────────
+0    0E 00         opcode = 0x000E（HELLO）
+2    53 00         version = 0x0053 = 83（LE）
+4    01 00         flag = 1
+6    31            subversion = '1' = 0x31
+7    46 72 7A 60   recvIv（客户端加密 → 服务端解密用的 IV）
+11   52 30 78 C1   sendIv（服务端加密 → 客户端解密用的 IV）
+15   08            终止符
```

**方向对应关系**：

```
服务端                                   客户端
sendIv {R,0,x,C1}  ────加密───▶  用 {R,0,x,C1} 解密
recvIv {F,r,z,60}  ◀────解密───  用 {F,r,z,60} 加密
```

## 2. AES-OFB 加解密（MapleAESOFB）

### 加密/解密流程（crypt 函数）

对应 [MapleAESOFB.java:109-135](../gms-server/src/main/java/org/gms/net/encryption/MapleAESOFB.java#L109-L135)。

```
输入: data（要加/解密的字节数组）
AES key: 硬编码的 32 字节密钥

1. 把 4 字节 IV 重复 4 遍 → 得到 16 字节的 AES 输入块
   例: IV={F,r,z,`} → myIv={F,r,z,`, F,r,z,`, F,r,z,`, F,r,z,`}

2. AES 加密 myIv → 得到 16 字节的密钥流

3. 密钥流 XOR data[0..15] → 得到明文/密文的前 16 字节

4. 把 AES 的输出再喂回 AES → 生成下一段 16 字节密钥流

5. 继续 XOR data[16..31], data[32..47]...

6. 全部处理完后，调用 updateIv() 轮转 IV（为下一个包做准备）
```

**示意图**：

```
IV={F,r,z,`} 重复4次 ──▶ AES加密 ──▶ 密钥流[0..15]  ──XOR──▶ 输出[0..15]
                                    │
                                    └──▶ AES加密 ──▶ 密钥流[16..31] ──XOR──▶ 输出[16..31]
                                                        │
                                                        └──▶ AES加密 ──▶ ...
```

### ⚠️ 关键陷阱：加密时的操作顺序

Java 的 `encode()` 顺序（[GMSV83PacketProtocol.java:59-67](../gms-server/src/main/java/org/gms/net/encryption/protocol/GMSV83PacketProtocol.java#L59-L67)）：

```java
public void encode(ChannelHandlerContext ctx, Packet in, ByteBuf out) {
    byte[] packet = in.getBytes();
    out.writeBytes(getEncodedHeader(packet.length)); // ① 先算包头（用当前 IV）
    MapleCustomEncryption.encryptData(packet);        // ② 混淆
    sendCypher.crypt(packet);                         // ③ AES（会更新 IV）
    out.writeBytes(packet);
}
```

**包头必须在 `crypt()` 之前生成**！因为 `crypt()` 会调用 `updateIv()` 修改 IV 状态，如果在之后生成包头，包头会使用错误的 IV，导致对端校验失败。

解密时同理，包头校验在 `crypt()` 之前（[GMSV83PacketProtocol.java:30-42](../gms-server/src/main/java/org/gms/net/encryption/protocol/GMSV83PacketProtocol.java#L30-L42)）：

```java
public void decode(ChannelHandlerContext context, ByteBuf in, List<Object> out) {
    final int header = in.readInt();                     // ① 读包头
    if (!receiveCypher.isValidHeader(header)) { ... }    // ② 校验（当前 IV）
    byte[] packet = new byte[decodePacketLength(header)];
    in.readBytes(packet);
    receiveCypher.crypt(packet);                         // ③ 解密（会更新 IV）
    MapleCustomEncryption.decryptData(packet);           // ④ 反混淆
    out.add(new ByteBufInPacket(Unpooled.wrappedBuffer(packet)));
}
```

### 包头格式与合法性校验

每个加密包前面有 4 字节包头，同时编码了版本校验信息和包体长度。

**包头编码**（[MapleAESOFB.java:141-153](../gms-server/src/main/java/org/gms/net/encryption/MapleAESOFB.java#L141-L153)）：

```java
int iiv = (iv[3] & 0xFF) | ((iv[2] << 8) & 0xFF00);
iiv ^= mapleVersion;                         // XOR 版本号
int mlength = ((length << 8) & 0xFF00) | (length >>> 8);  // 字节交换
int xoredIv = iiv ^ mlength;
// 输出: [iiv高字节, iiv低字节, xoredIv高字节, xoredIv低字节]
```

**包头校验**（[MapleAESOFB.java:166-171](../gms-server/src/main/java/org/gms/net/encryption/MapleAESOFB.java#L166-L171)）：

```java
// 取 header 的 [0][1] 两个字节，与 iv[2][3] XOR，应等于 mapleVersion 的高低字节
boolean valid = ((header[0] ^ iv[2]) & 0xFF) == ((mapleVersion >> 8) & 0xFF)
             && ((header[1] ^ iv[3]) & 0xFF) == (mapleVersion & 0xFF);
```

**包体长度解码**（[GMSV83PacketProtocol.java:53-56](../gms-server/src/main/java/org/gms/net/encryption/protocol/GMSV83PacketProtocol.java#L53-L56)）：

```java
// header 是 4 字节 int
int length = ((header >>> 16) ^ (header & 0xFFFF));  // 高16位 XOR 低16位
length = ((length << 8) & 0xFF00) | ((length >>> 8) & 0xFF);  // 字节交换
```

**校验失败 = IV 不匹配**。如果服务端的 IV 和加密时用的 IV 不同，包头校验必然失败。

### IV 轮转（updateIv / getNewIv）

每次 `crypt()` 执行完毕后，调用 `getNewIv()` 轮转 IV（[MapleAESOFB.java:173-179](../gms-server/src/main/java/org/gms/net/encryption/MapleAESOFB.java#L173-L179)）。这样即使两个包的内容完全相同，加密后的密文也不同。

## 3. 自定义混淆（MapleCustomEncryption）

在 AES-OFB 之外，冒险岛还有一层**自定义的 6 轮字节混淆**，增加逆向难度。

加密流程：`原始数据 → encryptData() → AES-OFB crypt → 密文`
解密流程：`密文 → AES-OFB crypt → decryptData() → 原始数据`

`decryptData()` 的逻辑（[MapleCustomEncryption.java:72-107](../gms-server/src/main/java/org/gms/net/encryption/MapleCustomEncryption.java#L72-L107)）：
- 共 6 轮（j=1 到 6）
- j 为奇数时**反向遍历**数组，j 为偶数时**正向遍历**
- 每轮包含：循环移位、加减常量、XOR 等操作
- `encryptData()` 是其逆操作

## 5. 客户端数据解析（`LoginPasswordHandler.handlePacket` — 第48行）

此时收到的已经是**解密+反混淆后的明文**，被包装为 `InPacket`（实现类 `ByteBufInPacket`，基于 Netty 的 `ByteBuf`）：

```java
String login = p.readString();   // 账号名（2字节长度LE + UTF-8内容）
String pwd   = p.readString();   // 密码明文（同上）
p.skip(6);                       // 跳过6字节掩码填充
byte[] hwid = p.readBytes(4);    // 4字节硬件ID
```

### 登陆包体格式（解密后的 `InPacket` 内容）

```
字段       类型      长度       说明
──────────────────────────────────────
opcode     short     2 字节     01 00（LOGIN_PASSWORD，已在 PacketProcessor 中被读走）
login      string    2+N 字节   账号名（2字节长度前缀 + UTF-8内容）
password   string    2+N 字节   密码明文（同上）
padding    bytes     6 字节     客户端掩码，全是 0
hwid       bytes     4 字节     硬件ID指纹
```

### `readString()` 的实现

[ByteBufInPacket.java:52-57](../gms-server/src/main/java/org/gms/net/packet/ByteBufInPacket.java#L52-L57)：

```java
public String readString() {
    short length = readShort();           // 小端序读取2字节→字符串长度
    byte[] stringBytes = new byte[length];
    byteBuf.readBytes(stringBytes);       // 读取N字节原始数据
    return new String(stringBytes, CharsetConstants.getCharset(...));  // 按编码转String
}
```

## 6. 密码校验逻辑（`Client.login` — 第653行）

`LoginPasswordHandler` 调用 `c.login(login, pwd, hwid)` 进入 [Client.java:653-731](../gms-server/src/main/java/org/gms/client/Client.java#L653-L731)。

### 校验流程

1. **防爆破**：尝试次数超过4次，直接关闭连接返回`6`
2. **查库**：
   ```sql
   SELECT id, password, gender, banned, pin, pic, characterslots, tos, language
   FROM accounts WHERE name = ?
   ```
3. **多级密码校验**：
   - 如果 `password` 字段以 `$2` 开头（bcrypt hash 标志）→ 用 `BCrypt.checkpw()` 验证
   - 否则按**明文**、**SHA-1**、**SHA-512** 依次匹配（兼容老数据）
   - bcrypt 迁移模式：如果匹配的是旧 hash，自动升级为 bcrypt 并回写数据库
4. **同协议条款检测**：`tos` 字段为 0 表示未同意协议条款
5. **多开检测**：调用 `SessionCoordinator.attemptLoginSession()` 检查同账号/同 HWID 是否已在线

### 返回值含义

| loginok | 含义 |
|---------|------|
| 0 | 登陆成功 |
| 3 | 账号被封禁 |
| 4 | 密码错误 |
| 5 | 账号不存在（触发自动注册，需开启 `automatic_register` 配置） |
| 6 | 尝试次数过多 |
| 7 | 已在其他位置登录 |
| 10 | 远端处理中 |
| 13 | 远端达到连接上限 |
| 16 | 多账号尝试限制 |
| 17 | 远端已登录 |
| 23 | 未同意服务条款 |
| -10 | 需要迁移到 bcrypt（旧 hash 匹配） |
| -23 | 需要同意 TOS 并迁移到 bcrypt |

### Go vs Java 关键差异

| 要点 | Java | Go |
|------|------|----|
| `>>>` 无符号右移 | `>>>` 是无符号右移，`>>` 是算术右移 | 用 `uint32`/`uint16`，`>>` 就是逻辑右移 |
| byte 符号 | `byte` 是 `-128~127`，需 `& 0xFF` 转无符号 | `byte` 是 `uint8`，无需额外处理 |
| 位运算优先级 | `&` 和 `^` 同优先级 | `&` 优先级高于 `^`，需注意括号 |

## 关键点总结

- **密码是明文传输的**（客户端没有做 hash），依赖加密通道保护，服务器端存储的是 bcrypt/SHA hash
- 密码校验支持 **bcrypt、SHA-1、SHA-512** 三种格式，兼容历史数据，并支持自动迁移到 bcrypt
- 网络包经过两层保护：**AES-OFB 流密码** + **6 轮自定义混淆**
- IV 在每次 TCP 连接时随机生成，通过**未加密的 Hello 包**交换
- **加密时包头必须在 Crypt 之前生成**，否则 IV 状态不对导致解密失败
- 数据解析通过 Netty `ByteBuf` 实现，数值全部用**小端序（LE）**读取，字符串用**2字节长度前缀 + UTF-8内容**的格式
- 自动注册功能（`automatic_register` 配置项）：当账号不存在时，自动用客户端提交的密码创建账号
